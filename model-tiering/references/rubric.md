# 定档细则与实例

## 判定顺序（别倒过来）

先判「能不能一句话/一条命令解决」，再判「要不要读上下文」，最后才判「难不难」。
**最常见的浪费是：轻活因为「专业」被当成攻坚。**

## 信号表

| 信号 | 轻（最弱档） | 中（居中档） | 高（最强档） |
|---|---|---|---|
| 步骤数 | 1 | 2–5 | 6+ 或不可预知 |
| 要改的文件 | 0–1 | 1–2 | 2+ 且互相关联 |
| 要读的上下文 | 无 | 1–2 个文件 | 3+ 文件 / 整仓 |
| 试错 | 不需要 | 可能 1 次 | 多轮假设-验证 |
| 验收 | 一眼看出 | 脚本/测试可判 | 人工评审、线上观察 |
| 失败后果 | 再问一次 | 重跑 | 回滚或不可逆 |

取**最高档**，再做一次降档核对：这个档的判据里有没有不成立的？有一条不成立就降一档试，失败再升——升档比重派贵。

档位名因模型而异：先 `list_subagent_models(provider, model)` 拿到它支持的档位（升序），
再用 `tier.mjs map --efforts "..."` 映射成轻/中/高。别把 `low/high/max` 当成通用答案。

## 实例

**例 1：把这份 md 里的邮箱都提取出来** → 轻。一条正则，结果可数，不派单。

**例 2：12 个 csv 合并成 xlsx，按日期排序** → 中。自包含、可校验；派子代理时带 `reasoning_effort: "high"`。

**例 3：给 Electron 应用加一个「上次使用的模型」记忆** → 高。要读主进程/渲染/配置三处，靠构建验证；派子代理带 `reasoning_effort: "max"`，要求先回 5 行改动计划。

**例 4：线上偶发卡死、日志无明显报错** → 高。多轮假设-验证；要求子代理每轮只回「假设 + 证据 + 下一步」。

**例 5：把这段文案改得口语一点** → 轻。只是改写，不查证、不派单。

## 三个误判

1. **「用户很急」≠ 高档**：急的时候更该拆小并行，不是换个更慢的思考。
2. **「要写得好看」≠ 高档**：文案质量靠提示词和迭代。
3. **「我怕出错」≠ 高档**：加一条验收判据比升档便宜得多。

## 不分档的时候

- 闲聊、情绪回应、群聊接话：不加载本 skill。
- 一次工具调用就出结果：直接做。
- 用户说「这次用好模型/认真点」：照办，并说明不走省钱策略。
